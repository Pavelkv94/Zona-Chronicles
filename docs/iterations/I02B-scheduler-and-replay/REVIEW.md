## BLOCKER 1 (архитектура) — отвергнутая команда завершения делает journey невосстановимо
незавершённым. Закрыто.

**Механизм.** `runWorldTick` читал версию мира и клал её в `expected_world_version`. Между этим
чтением и замком внутри `executeCommand` версия могла уйти вперёд → `stale_world_version`. Отказ
записывался в journal под `command_id`, детерминированно выведенным из `action_id`. Дальше
выхода не было: поле входит в отпечаток команды, поэтому следующая попытка собирала другую
версию → `fingerprint-mismatch` → `precondition_failed` вечно. Агент оставался `traveling`
навсегда; в append-only журнале — `journey.started` без завершения; `world tick` возвращал
exit 0.

**Воспроизведено lead-ом самостоятельно.** Первая проба (12 агентов, одинаковый `due_at`) НЕ
воспроизвела — окно узкое. Со ступенчатыми сроками воспроизвелось сразу:

```text
ЗАСТРЯЛИ 3: agent:r2,agent:r3,agent:r5 | завершено 3/6
```

**Закрыто тремя слоями, и второй с третьим вскрылись только после починки предыдущего:**

1. `expected_world_version` стал НЕОБЯЗАТЕЛЬНЫМ (ADR-011 §11.1). Команды расписания его не
   ставят: действие породил сам мир, проверять нечего, а сериализацию даёт замок.
2. После этого проба упала иначе — «мировое время не может идти назад». Два worker-а берут
   действия с РАЗНЫМИ `due_at`, и более раннее откатывает часы. Параллелизм на одном мире
   несовместим с одними монотонными часами — ровно поэтому §5 `03_TECHNICAL_DESIGN` требовал
   advisory lock мира, а отклонение I02A §8.4 назвало его безобидным. Замок возвращён
   (ADR-011 §11.2), `pg_try_advisory_lock`: второй worker не ждёт, а возвращает пустой шаг.
3. И только тогда стало видно третье: записанный отказ делает действие вечным — оно
   возвращается в очередь каждым тиком. Добавлены `failed_at`/`failure_code` (миграция 0008) и
   исключение из захвата (ADR-011 §11.3).

Тест на конечность исхода постоянный (`scheduler-failure.integration.test.ts`); мутация «не
помечать отвергнутое» его роняет.

## BLOCKER 2 (архитектура) — `loadWorldState` читает мир вне транзакции. ПРИНЯТО, не закрыто.

Четыре отдельных запроса под `read committed` могут вернуть состояние, которого в мире не было:
`agents` уже содержит эффект события N+1, а `worlds.last_sequence` — ещё нет. Ревьюер
воспроизвёл 9 несвязных чтений из 454 при работающем worker-е.

**Статус: открыто, зафиксировано как долг I03.** Обоснование решения не закрывать сейчас: с
advisory lock мира (ADR-011 §11.2) единственный писатель на мир сериализован, поэтому окно
осталось только между внешней командой и параллельным чтением. Правка требует либо транзакции
на чтение, либо сборки состояния одним запросом — и то, и другое затрагивает горячий путь,
который в этой итерации уже переписан трижды. Вносить четвёртую правку без раунда верификации
после неё — ровно то, от чего эта итерация пострадала.

**Обязательно к исполнению в I03** вместе с проекциями: они читают то же состояние, и там же
уместно правило из предложения ревьюера — любое чтение, становящееся артефактом, выполняется
в одной транзакции.

### Что вскрылось при закрытии C4 и стоит запомнить

Первая версия нового теста тоже не различала. Порядок обеспечивают ТРИ избыточных слоя (индекс,
`ORDER BY`, JS-сортировка), и они маскируют друг друга. Измерено:

```text
убрать entity_id из order by  -> проходит (план идёт по индексу)
убрать JS-сортировку          -> проходит (порядок задан SQL)
убрать всё три                -> падает: z99,z98 вместо z96,z97
```

В докстринге теста записано прямо: он доказывает свойство, но НЕ обнаруживает утрату одного
слоя. Написать «обнаруживает удаление entity_id из ORDER BY» было бы неправдой.

### Проба M3: обе стороны контроля

Красный записан до правки — снимок, снятый под `prng_version: xoshiro256++/2`, ЗАГРУЗИЛСЯ вместо
отказа. Вторая сторона проверена мутацией `majorMinor` → тождественная функция: тогда падает тест
на patch-версию Node, то есть контроль начинает отвергать корректный случай.

```text
без проверки   -> снимок с чужим prng_version загружается молча
majorMinor=id  -> × «расхождение patch-версии Node не мешает восстановлению»
как есть       -> оба теста зелёные
```

### Что вскрыло расширение C10 (M6)

Расширение привязки правила с одного файла до соглашения об именовании обнаружило дефект,
которого находки не содержали: блок C10 переопределял `no-restricted-imports` ЦЕЛИКОМ, поэтому
запрет LLM SDK (ADR-006) внутри replay-файлов не действовал — и не действовал ровно с того дня,
как правило появилось. Правила eslint не сливаются; это записано в самом конфиге строкой выше по
файлу, и всё равно было нарушено во второй раз.

```text
без patterns: [...llmImportRestrictions]  -> × «запрет LLM SDK не исчезает в replay-файлах»
привязка к одному пути                    -> × фикстура нарушения не ловится
как есть                                  -> три фикстуры зелёные
```

Предел новой привязки записан в конфиге явно: replay в файле с другим именем из-под правила
уходит. Сильнее выразить нельзя — запретить `decide` всему `persistence` невозможно,
`command-handler.ts` вызывает его законно.

### Отклонение от PLAN §4.6, принятое при закрытии M4

PLAN требовал источник, «восстанавливающий позиции из снимка». Сделано иначе: позиции живут в
строке `worlds` (миграция 0009) и двигаются в ТОЙ ЖЕ транзакции, что событие; снимок их только
фотографирует.

Причина — буква PLAN даёт неверный результат. Снимок берётся оператором по его решению (OPS-04),
а не непрерывно: между двумя снимками мир принимает сколько угодно команд. Источник, стартующий с
позиций последнего снимка, повторил бы уже сделанные розыгрыши, то есть выдал бы одни и те же
значения дважды при том же seed. Заметить это было бы нечем, кроме подозрительно похожего мира.
Позиция обязана двигаться там же, где `last_sequence`.

Побочно закрыт документированный костыль CLI: `world snapshot` брал позиции из последнего снимка,
а при его отсутствии пересчитывал `seedWorld(seed)`. Допущение было записано честно («пересмотреть
в тот день, когда появится команда, которая бросает кости»), но оставалось допущением.

**Что осталось недоказанным и почему.** Правило «позиция двигается только на ПРИНЯТОЙ команде»
(иначе replay, который проигрывает лишь события, разошёлся бы с непрерывным прогоном) выполнено
конструкцией — запись идёт в ветке accepted, — но тестом не покрыто: ни одна команда I02B
розыгрышей не делает, поэтому тест на отказе прошёл бы одинаково при любой реализации. Зелёный
тест здесь был бы ложным доказательством, поэтому правило записано в коде причиной, а не тестом.
Первая механика с розыгрышем обязана принести это покрытие.

```text
источник без startPositions -> × «принятая команда сохраняет позиции мира»
как есть                    -> три теста зелёные
```

Затронут и тест обновления `upgrade-path`: он моделировал «предыдущую поставку» ТЕКУЩИМ
`initializeWorld`, и миграция 0009 это вскрыла — писатель новой поставки не может писать в схему
старой. Смысл фазы `expand` обратный, поэтому мир до обновления теперь пишется явным SQL прежней
поставки. Обещание теста не изменилось.

## Процесс: что показала параллельная работа

Три сессии (lead и два исполнителя) дали реальный выигрыш по времени и вскрыли три дефекта моих
решений. Цена: **атрибуция терялась трижды**.

1. Мои `git add -A` дважды подобрали файлы задачи T2 и закоммитили под сообщениями о моей
   работе (`55b6e0e`, `97b0a67`). Авторство восстановлено в `PLAN.md` §8, в истории — нет.
2. SubagentStop обвинил read-only test-reviewer-а в моих файлах, пока я чинил blocker
   параллельно его работе. Он не тронул чужое, не потребовал расширения прав, сообщил и ждал.

Вывод, теперь подпёртый тремя случаями: параллельные исполнители обязаны быть отдельными
СЕССИЯМИ с собственным worktree, а не in-process subagent-ами. До этого — `git add -A` при
параллельной работе применять нельзя.

## Что нашли исполнители в моих решениях

- **T1** (`i02b-t1-cli`): in-process subagent наследует cwd родителя, поэтому модель
  `pnpm task:worktree` для него не работает; `world tick` без флагов в demo ничего не делает.
- **T2** (`i02b-t2-snapshots`): `agent_type` в hook payload — это ИМЯ сессии, а не роль;
  `packages/contracts/**` — protected path, и выданный write set с ним пересекался; критерий
  C10 требовал механизма, которого по построению не может быть; правило границ для replay
  падало и на правильной реализации.

Ни один из них не обошёл контроль. Каждый раз останавливались и спрашивали.
