# I02B — ACCEPTANCE

Итерация: I02B «Scheduler, завершение journey и replay»
Заморожено: 2026-08-22, до начала реализации.
Нумерация продолжает I01 (A1–A11) и I02A (B1–B10): здесь **C1–C12**.

Каждый критерий исполняем. «Проверено вручную» приёмкой не является. Каждый новый инвариантный
тест сопровождается записанным выводом мутационной пробы, прогнанной ИЗОЛИРОВАННО
(`08_TDD_AND_AGENT_WORKFLOW` §7).

## C1. Принятая команда планирует своё завершение

**Given** мир с праздным агентом
**When** исполняется `journey.start` по маршруту длительностью `travelMinutes`
**Then** в `scheduled_actions` появляется ровно одна запись с `due_at = world_time + travelMinutes`,
**And** она создана в ТОЙ ЖЕ транзакции, что событие: сбой в любой точке не оставляет ни
события без запланированного завершения, ни запланированного завершения без события.

## C2. Worker доводит journey до конца без участия человека

**Given** запланированное завершение с наступившим `due_at`
**When** worker обрабатывает due actions
**Then** появляется событие `journey.completed`,
**And** агент оказывается в конечной локации маршрута со статусом `idle`,
**And** запись `scheduled_actions` помечена выполненной, а не удалена,
**And** мировое время продвинуто к обработанному `due_at`.

## C3. Ненаступившее действие не исполняется

**Given** запланированное завершение с `due_at` в будущем относительно мирового времени
**When** worker обрабатывает due actions
**Then** событий не появляется и мировое время не меняется.

## C4. Порядок обработки не зависит от скорости процесса

**Given** несколько due actions с ОДИНАКОВЫМ `due_at`
**When** worker их обрабатывает
**Then** порядок задан `(priority, entity_id, action_id)` и воспроизводится побайтово между
прогонами,
**And** он тот же при разных размерах batch.

Проверка сравнивает журнал двух независимых прогонов, а не «выглядит стабильным».

## C5. Конкурентные worker-ы не исполняют действие дважды

**Given** несколько due actions и два worker-а на настоящих параллельных соединениях
**When** оба обрабатывают очередь
**Then** каждое действие исполнено ровно один раз,
**And** `sequence` в журнале без дыр и дублей,
**And** ни один worker не ждёт другого дольше, чем нужно (`SKIP LOCKED`, а не общая блокировка).

## C6. Истёкший lease подхватывается ровно один раз

**Given** действие, захваченное worker-ом, который умер, не завершив работу
**When** истекает lease
**Then** другой worker подхватывает действие,
**And** событие появляется ровно одно,
**And** первый worker, «ожив», не может завершить своё действие поверх чужого результата.

## C7. Остановка между стартом и завершением ничего не теряет

**Given** journey начат, worker не запускался
**When** процесс worker-а запускается заново
**Then** завершение происходит,
**And** каждому `journey.started` соответствует ровно одно `journey.completed`.

Проверка порождает настоящие процессы, а не переиспользует пул в одном.

## C8. Снимок содержит всё, что нужно для продолжения

**Given** мир с историей
**When** создан снимок
**Then** он содержит `last_sequence`, мировое время, позиции PRNG-потоков, каноническое
состояние, deterministic runtime profile и собственный checksum,
**And** уровень изоляции транзакции входит в runtime profile (ADR-010 §10.1),
**And** checksum снимка не зависит от профиля хоста (свойство B2 из I01 сохраняется).

## C9. Снимок плюс суффикс журнала равен непрерывному прогону

**Given** мир, прогнанный до `sequence = N` непрерывно
**When** тот же мир восстановлен из снимка на `sequence = K < N` и к нему применён суффикс
журнала `K+1..N`
**Then** каноническое состояние и его checksum совпадают побайтово с непрерывным прогоном.

## C10. Replay не выполняет ни одного розыгрыша

**Given** журнал, содержащий события с `random_audit`
**When** выполняется replay
**Then** результат совпадает с записанным,
**And** путь replay СТРУКТУРНО не может обратиться к случайности: модуль replay не зависит ни
от `decide`, ни от источника случайности, и это проверяется контролем границ, а не намерением.

### Change request (2026-08-22, решение lead-а по вопросу исполнителя I02B-T2)

Исходная формулировка требовала «источник случайности, подставленный в replay, не вызывается ни
разу; отсутствие розыгрыша доказывается отказом». Исполнитель заметил, что подставить такой
источник **некуда**: replay — это свёртка `evolve` по суффиксу журнала, а `evolve(state, event)`
чист и `RandomSource` не принимает вовсе. Параметр пришлось бы добавить в сигнатуру специально
ради теста — то есть завести в продукте шов, существующий только чтобы его проверяли.

Замечание принято, но критерий не ослаблен, а усилен. Структурная невозможность сильнее
проверки поведения: у теста с падающим источником есть один прогон, у запрета в контроле — все.
Слабое место структурного довода ровно одно: он держится, только пока replay остаётся свёрткой.
Если когда-нибудь его перепишут через повторный `decide`, довод исчезнет молча — поэтому запрет
вынесен в контроль, который упадёт в тот самый день.

**Поправка к change request (тот же день, найдено исполнителем I02B-T3).** Первая редакция
запрета была правилом `.dependency-cruiser.cjs` с `reachable: true`, и она оказалась
НЕВЫПОЛНИМОЙ: `depcruise` строит граф по файлам, а `@zona/domain` — баррель, реэкспортирующий
и `evolve`, и `decide` из одного `index.ts`. Любая реализация replay, которой нужен `evolve`,
транзитивно «достигает» `decide`, то есть правило падало и на правильном коде.

Моя проба этого не показала, потому что проверила только одно направление — «нарушение
ловится», — и не проверила второе: «корректный код проходит». Это пятый случай того же класса
за две итерации, и первый — в контроле, который я добавлял именно затем, чтобы не полагаться на
слабое доказательство.

Запрет переехал в `eslint.config.mjs`: eslint видит ИМЕНОВАННЫЕ импорты, а не файлы, поэтому
выражается точно — `evolve` можно, `decide` и источники случайности нельзя. Проверены ОБА
направления: корректная реализация проходит, импорт `decide` и импорт `DeterministicRandomSource`
дают названный отказ.

Синтетический `random_audit` в журнале остаётся в тесте, но как проверка round-trip поля, а не
как доказательство C10.

## C11. Позиции PRNG переживают перезапуск

**Given** мир, в котором было сделано N розыгрышей
**When** процесс перезапущен и состояние восстановлено из снимка
**Then** следующий розыгрыш продолжает поток с позиции N, а не начинает его заново.

## C12. Мировое время монотонно

**Given** любая последовательность обработанных действий
**Then** мировое время не убывает ни разу и не обгоняет `due_at` последнего обработанного
действия.

Проверяется property-тестом на случайных последовательностях, а не одним сценарием.

## Что НЕ является приёмкой

- зелёный `pnpm verify` без запущенной базы;
- «worker выглядит работающим» без остановки посреди работы;
- replay, сверенный сам с собой, а не с непрерывным прогоном;
- порядок обработки, проверенный одним прогоном.
