# I01 — ACCEPTANCE

Замораживается до реализации. Изменение любого критерия требует отдельного change request с
объяснением изменившегося поведения, а не удобства при сдаче.

Формат: **Given / When / Then**. Каждый критерий обязан быть исполняемым.

## A1. Одинаковый seed даёт побайтово одинаковый мир (SIM-01)

**Given** фиксированный seed `S` и immutable bundles rules/content/schema
**When** мир порождается 100 раз в **разных процессах**
**Then** canonical JSON и checksum совпадают во всех 100 прогонах

Разные процессы обязательны: одинаковый результат внутри одного процесса не исключает
зависимости от порядка инициализации модулей или от накопленного состояния.

## A2. Разный seed даёт другой, но валидный мир

**Given** seeds `S1 != S2`
**When** порождаются два мира
**Then** их checksum различаются, и оба проходят runtime-валидацию схем

Критерий существует, чтобы A1 нельзя было выполнить константой.

## A3. Locale, timezone и порядок ключей не влияют на результат (SIM-01)

**Given** тот же seed
**When** прогон выполняется под `TZ=Pacific/Chatham LC_ALL=tr_TR.UTF-8`, затем под
`TZ=UTC LC_ALL=C`, а объекты состояния строятся с разным порядком вставки ключей
**Then** canonical JSON и checksum идентичны во всех вариантах

Турецкая локаль выбрана намеренно: она ломает регистр латиницы и выявляет скрытый
`toLowerCase`/`localeCompare`.

## A4. Envelopes валидируются в runtime, а не только типами

**Given** command и world event по `09_EVENT_AND_COMMAND_CONTRACTS` §2–3
**When** валидный envelope проходит round-trip parse → serialize → parse
**Then** результат идентичен исходному; **и** каждое из следующих нарушений отвергается с
типизированной ошибкой, а не молча принимается:
лишнее поле, отсутствующее обязательное поле, неверный тип, `world_time` без смещения,
`sequence` не целое, неизвестный `type`, `schema_version` другой мажорной версии.


### Change request к A4 (2026-08-21, решение lead-а)

Формулировка «результат идентичен исходному» уточняется: round-trip выполняется над
**декодированным** значением, а не над сырым текстом входа.

Причина. `09_EVENT_AND_COMMAND_CONTRACTS` §3 записывает `world_time` как `"…T18:20:00Z"`, без
миллисекунд. Отвергать пример из нормативного документа нельзя, поэтому декодер принимает любую
строгую метку с явным смещением и приводит её к канонической форме `…T18:20:00.000Z`. Без
нормализации один и тот же момент, записанный в разных смещениях, давал бы разный checksum —
прямое нарушение SIM-01.

Формально: `encode(decode(x)) === encode(decode(decode(x)))`.

Расхождение найдено contract-steward-ом при заморозке и вынесено как вопрос, а не закрыто
молча. Изменение сужает допустимое (канонический момент однозначен), а не ослабляет критерий.

## A5. `NaN`, `Infinity` и неописанное округление отвергаются

**Given** числовое поле canonical state или payload
**When** значение равно `NaN`, `Infinity`, `-Infinity` либо имеет больше знаков, чем допускает
документированная единица
**Then** валидация отвергает его на границе домена, а не округляет молча

## A6. Порты — единственный источник времени, случайности и ID

**Given** `packages/domain` и `packages/simulation`
**When** выполняется `pnpm lint` и `pnpm boundaries:check`
**Then** отсутствуют `Date.*`, `Math.random`, `crypto`, `perf_hooks`, сеть, файловая система и
`process`; время, случайность, ID и коэффициенты приходят через `Clock`, `RandomSource`,
`IdFactory`, `Ruleset`

Проверка уже исполняется gate-ом I00; здесь она подтверждается на первом настоящем доменном коде.

## A7. Случайность воспроизводима и разделена по потокам

**Given** `RandomSource` с seed `S` и stream key `K`
**When** выполняется последовательность draw
**Then** та же пара `(S, K)` даёт ту же последовательность, а разные `K` при одном `S` дают
независимые последовательности; каждый draw сообщает audit-поля (stream key, draw index)

## A8. `evolve` обрабатывает все типы событий исчерпывающе

**Given** union типов событий v1
**When** добавляется новый тип события без ветки в `evolve`
**Then** сборка падает на этапе компиляции

Проверяется отрицательным type-тестом, а не только зелёным прогоном.

## A9. Snapshot ссылается на bundles по версии и checksum

**Given** порождённый мир
**When** строится snapshot
**Then** он содержит версии и checksum rules/content/schema bundles; подмена содержимого bundle
без изменения версии обнаруживается

## A10. CLI демонстрирует мир без базы данных

**Given** чистый clone и отсутствие запущенного PostgreSQL
**When** выполняется `pnpm world seed --seed 42`, затем `pnpm world inspect --seed 42`
**Then** первая команда печатает canonical JSON и checksum, вторая — агентов, локации и
маршруты; обе завершаются кодом 0 и не открывают сетевых соединений

### Change request к A10 (2026-08-21, решение lead-а)

В `--seed 42` у второй команды. Исходная формулировка (`pnpm world inspect` без seed) была
внутренне противоречива: §2 плана требует, чтобы CLI работал **in-memory, без БД**, а между
двумя отдельными запусками `pnpm` состояние не сохраняется — значит голый `world inspect` не
может знать, какой мир был порождён последним, без скрытого seed по умолчанию или без
персистентности, которую итерация прямо исключает.

Раздел ручного demo уже использовал `--seed 42`; исправлена именно формулировка критерия,
а не поведение CLI. Найдено acceptance-author-ом, вынесено как вопрос и не обойдено
костылём на стороне реализации.

### Форма вывода `world seed` (решение lead-а, чтобы I01-T4 не гадал)

`world seed --seed <N>` печатает в stdout **одну строку**: canonical JSON снимка
(`SnapshotSchema`), включая поле `checksum`. Отдельной строки с checksum нет — снимок
самодостаточен (A9), а canonical JSON по определению однострочный. Валидация в тестах
выполняется `decodeSnapshot`/`verifySnapshotChecksum` из `@zona/contracts`.

## Ручной demo (записывает владелец)

1. `pnpm world seed --seed 42 > /tmp/a.json` и то же во втором терминале в `/tmp/b.json`;
   `diff /tmp/a.json /tmp/b.json` пуст.
2. `pnpm world seed --seed 43` даёт другой checksum.
3. `pnpm world inspect --seed 42` показывает читаемый состав мира.

## Что НЕ является приёмкой

- зелёный gate сам по себе — он не отличает «детерминировано» от «всегда возвращает пустое»;
- одинаковый результат в одном процессе;
- property-тест, чей генератор не достигает границы проверяемого условия — урок I00-F5:
  генератор с `day <= 28` не проверял правило високосных столетий, оставляя набор зелёным.
