## Процессный finding

Architecture reviewer работал одновременно с test reviewer-ом, который по своей роли
временно мутирует production-код для проверки силы тестов. Из-за этого часть evidence
снималась с изменяющегося рабочего дерева (обнаружены чужие временные правки в
`packages/persistence`). Committed HEAD при этом не менялся, и аудит был завершён по
`git archive HEAD`.

**Вывод для процесса:** reviewer обязан работать по замороженному SHA или в отдельном
worktree, а два reviewer-а не запускаются параллельно в общем дереве, если один из них
мутирует код. Это ошибка оркестрации lead-а, а не участников.

### B2 подтверждён на живом примере

Во время rework-раунда один из implementer-субагентов выполнил `git stash` / `git stash pop`
в общем рабочем дереве, где параллельно работали ещё две задачи, — операцию, запрещённую
и заданием, и `decide-bash.ts`. Hook её не заблокировал, потому что `.claude/writeset.json`
отсутствовал, и сессия была классифицирована как `lead`.

Это ровно тот отказ, который описан в B2: **отсутствие дискриминатора роли было fail-open**.
Агент сообщил об операции честно и восстановил состояние; проверка lead-ом показала пустой
`git stash list` и сохранность файлов параллельных задач. Ущерба нет, но контроль не сработал,
и это лучшее возможное обоснование фикса B2 (положительный признак роли из hook payload,
task-сессия без write set = deny).

## Предложения по ADR (требуют решения владельца)

1. **Правка ADR-002** — ребро `api → persistence` удалено; зафиксировать, что observer path
   получает данные только через `projections`.
2. **Новый ADR: license policy по границе дистрибуции** — раздельные production/development
   allowlists и исполняемое утверждение об отсутствии weak copyleft в production-графе.
3. **Правка ADR-008 (семантика исключений)** — `scope` обязан идентифицировать экземпляр
   (`package@version`, путь, advisory id), а не правило или категорию; Red-тест на каждую проверку.
4. **Новый ADR: идентичность агентной сессии** — различение task/lead выводится из
   неподделываемого сигнала; отсутствие write set в subagent-сессии означает deny.
5. **Правка ADR-003 / SIM-01** — перечислить полную поверхность недетерминизма (глобалы
   `crypto`/`fetch`, `Intl`/locale API, `process.hrtime`, `Date.parse`) и обязать fixture-suite
   в gate: список запретов стоит ровно столько, сколько стоят его тесты.

## Раунд 2 (проверяемый commit `789a8d5`) — реестр утрачен

**Это finding M-6 третьего раунда, а не примечание.** Отчёт независимого ревьюера раунда 2
никогда не был внесён в этот файл, а его исходный текст невосстановим: транскрипты субагентов
не сохраняются, а часть сессии lead-а заменена summary при компактификации контекста.

Известно достоверно только следующее: раунд 2 дал `FAIL (3 blocker, 9 major)` против `789a8d5`,
и коммит `b247f42` заявлен как закрывающий все его findings.

Всё остальное, чем располагает проект, — метки `N*`/`minor*` в docstring-ах исходников,
то есть **формулировка автора фикса, а не ревьюера**:

| Метка | Где записана | Суть в изложении автора фикса |
|---|---|---|
| N1 | `task-ownership.ts:32`, `hooks/subagent-stop-writeset.ts:16` | совпадение с `lead_paths` трактовалось как владение и в task-сессии |
| N2 | `decide-bash.ts:26`, `git-source.ts:5`, `writeset.test.ts:55`, `cli/verify-task-ownership.ts:15` | источник ограничений читался с диска, доступного ограничиваемой сессии |
| minor 4 | `session-role.ts:20` | `agent_type` может присутствовать и у главного потока |
| minor 5 | `boundary-fixtures.test.ts:15` | sweep осиротевших фикстур |

Метки N3–N11, упомянутые в `b247f42`, в коде как таковые не размечены и восстановлению
из независимого источника не поддаются.

Практическое следствие для gate: **закрытие раунда 2 непроверяемо против независимой
формулировки**. Реконструкция колонки «заявлено», выполненная ревьюером раунда 3, опирается на
те же docstring-и, то есть на позицию автора фикса — ровно то, чего роль reviewer-а обязана
избегать. Это не означает, что фиксы неверны: раунд 3 проверил их против кода и подтвердил
большинство. Это означает, что утверждение «findings раунда 2 закрыты» опирается на слово
автора фикса и не может быть проверено иначе.

### Процессное правило, введённое по итогам M-6

Отчёт независимого ревьюера вносится в `REVIEW.md` **дословно и в момент получения**, до начала
работ по фиксам. Пересказ отчёта после закрытия findings доказательством не является: он
неотличим от изложения автора фикса. Evidence, существующая только в контексте модели, —
не evidence (ADR-008).

## Раунд 3, верификационный (проверяемый диапазон `789a8d5..3fe7ce3`)

Две независимые read-only сессии, обе с запретом на изменение рабочего дерева.

- Test reviewer (Sonnet): `RESULT: PASS` — 0 blocker, 0 major, 4 minor.
- Architecture reviewer (Opus): `RESULT: FAIL (2 blocker, 8 major)`.

Вердикты не противоречат друг другу. Формулировка архитектурного ревьюера:

> Мутационное тестирование измеряет силу тестов относительно существующего кода; оно не может
> обнаружить **отсутствующее** правило, потому что для отсутствующего правила нет мутанта.

Тест на `core-has-no-adapter-dependencies` честно краснеет при удалении правила — и при этом не
знает, что regex этого правила не содержит `node:crypto`. Это аргумент за то, чтобы две роли
оставались раздельными, а не сливались в одну «проверку качества».

Решение итерации по результатам раунда 3 — **REWORK**.
