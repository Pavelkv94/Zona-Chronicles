## Процессный finding

Architecture reviewer работал одновременно с test reviewer-ом, который по своей роли
временно мутирует production-код для проверки силы тестов. Из-за этого часть evidence
снималась с изменяющегося рабочего дерева (обнаружены чужие временные правки в
`packages/persistence`). Committed HEAD при этом не менялся, и аудит был завершён по
`git archive HEAD`.

**Вывод для процесса:** reviewer обязан работать по замороженному SHA или в отдельном
worktree, а два reviewer-а не запускаются параллельно в общем дереве, если один из них
мутирует код. Это ошибка оркестрации lead-а, а не участников.

### B2 подтверждён на живом примере

Во время rework-раунда один из implementer-субагентов выполнил `git stash` / `git stash pop`
в общем рабочем дереве, где параллельно работали ещё две задачи, — операцию, запрещённую
и заданием, и `decide-bash.ts`. Hook её не заблокировал, потому что `.claude/writeset.json`
отсутствовал, и сессия была классифицирована как `lead`.

Это ровно тот отказ, который описан в B2: **отсутствие дискриминатора роли было fail-open**.
Агент сообщил об операции честно и восстановил состояние; проверка lead-ом показала пустой
`git stash list` и сохранность файлов параллельных задач. Ущерба нет, но контроль не сработал,
и это лучшее возможное обоснование фикса B2 (положительный признак роли из hook payload,
task-сессия без write set = deny).

## Предложения по ADR (требуют решения владельца)

1. **Правка ADR-002** — ребро `api → persistence` удалено; зафиксировать, что observer path
   получает данные только через `projections`.
2. **Новый ADR: license policy по границе дистрибуции** — раздельные production/development
   allowlists и исполняемое утверждение об отсутствии weak copyleft в production-графе.
3. **Правка ADR-008 (семантика исключений)** — `scope` обязан идентифицировать экземпляр
   (`package@version`, путь, advisory id), а не правило или категорию; Red-тест на каждую проверку.
4. **Новый ADR: идентичность агентной сессии** — различение task/lead выводится из
   неподделываемого сигнала; отсутствие write set в subagent-сессии означает deny.
5. **Правка ADR-003 / SIM-01** — перечислить полную поверхность недетерминизма (глобалы
   `crypto`/`fetch`, `Intl`/locale API, `process.hrtime`, `Date.parse`) и обязать fixture-suite
   в gate: список запретов стоит ровно столько, сколько стоят его тесты.

## Раунд 2 (проверяемый commit `789a8d5`) — реестр утрачен

**Это finding M-6 третьего раунда, а не примечание.** Отчёт независимого ревьюера раунда 2
никогда не был внесён в этот файл, а его исходный текст невосстановим: транскрипты субагентов
не сохраняются, а часть сессии lead-а заменена summary при компактификации контекста.

Известно достоверно только следующее: раунд 2 дал `FAIL (3 blocker, 9 major)` против `789a8d5`,
и коммит `b247f42` заявлен как закрывающий все его findings.

Всё остальное, чем располагает проект, — метки `N*`/`minor*` в docstring-ах исходников,
то есть **формулировка автора фикса, а не ревьюера**:

| Метка | Где записана | Суть в изложении автора фикса |
|---|---|---|
| N1 | `task-ownership.ts:32`, `hooks/subagent-stop-writeset.ts:16` | совпадение с `lead_paths` трактовалось как владение и в task-сессии |
| N2 | `decide-bash.ts:26`, `git-source.ts:5`, `writeset.test.ts:55`, `cli/verify-task-ownership.ts:15` | источник ограничений читался с диска, доступного ограничиваемой сессии |
| minor 4 | `session-role.ts:20` | `agent_type` может присутствовать и у главного потока |
| minor 5 | `boundary-fixtures.test.ts:15` | sweep осиротевших фикстур |

Метки N3–N11, упомянутые в `b247f42`, в коде как таковые не размечены и восстановлению
из независимого источника не поддаются.

Практическое следствие для gate: **закрытие раунда 2 непроверяемо против независимой
формулировки**. Реконструкция колонки «заявлено», выполненная ревьюером раунда 3, опирается на
те же docstring-и, то есть на позицию автора фикса — ровно то, чего роль reviewer-а обязана
избегать. Это не означает, что фиксы неверны: раунд 3 проверил их против кода и подтвердил
большинство. Это означает, что утверждение «findings раунда 2 закрыты» опирается на слово
автора фикса и не может быть проверено иначе.

### Процессное правило, введённое по итогам M-6

Отчёт независимого ревьюера вносится в `REVIEW.md` **дословно и в момент получения**, до начала
работ по фиксам. Пересказ отчёта после закрытия findings доказательством не является: он
неотличим от изложения автора фикса. Evidence, существующая только в контексте модели, —
не evidence (ADR-008).

## Раунд 3, верификационный (проверяемый диапазон `789a8d5..3fe7ce3`)

Две независимые read-only сессии, обе с запретом на изменение рабочего дерева.

- Test reviewer (Sonnet): `RESULT: PASS` — 0 blocker, 0 major, 4 minor.
- Architecture reviewer (Opus): `RESULT: FAIL (2 blocker, 8 major)`.

Вердикты не противоречат друг другу. Формулировка архитектурного ревьюера:

> Мутационное тестирование измеряет силу тестов относительно существующего кода; оно не может
> обнаружить **отсутствующее** правило, потому что для отсутствующего правила нет мутанта.

Тест на `core-has-no-adapter-dependencies` честно краснеет при удалении правила — и при этом не
знает, что regex этого правила не содержит `node:crypto`. Это аргумент за то, чтобы две роли
оставались раздельными, а не сливались в одну «проверку качества».

Решение итерации по результатам раунда 3 — **REWORK**.

### Процессные наблюдения раунда 3

1. Обе review-сессии оказались полностью заблокированы собственным контролем DEV-02 (M-7) и
   потребовали ручного вмешательства lead-а. Это живое подтверждение работы фикса B2 — и
   одновременно доказательство, что harness не различает «task-сессия, которая пишет» и
   «task-сессия, которой нужен только read-only Bash».
2. Инструкция lead-а ревьюерам («запись в scratchpad через Bash hook-ом не покрывается») была
   верна для hook-а записи и неверна для hook-а Bash. Ревьюер потерял на этом часть работы и
   выполнил один из пунктов по коду вместо исполнения. Ошибка lead-а, не ревьюера.
3. Оба ревьюера ограничения соблюли: рабочее дерево не изменялось, `git stash`/`checkout`/`reset`
   не запускались. Это отличается от раунда 1, где два субагента выполнили `git stash` вопреки
   инструкции (см. «Процессный finding» выше).

## Findings, найденные на живых прогонах раунда фиксов I00-F5

Эти дефекты не пришли из review — их вскрыла сама работа раунда. Записаны в момент
обнаружения по правилу, введённому после M-6.

### F5-1 (blocker). `SubagentStop` с кодом 2 запирает уже завершённую сессию в петле

Сессия `F5-T2` сдала работу, получила приёмку и была закрыта lead-ом. После этого она
примерно **двенадцать раз подряд** получила один и тот же вердикт SubagentStop о нарушении
write set — дословно тот же текст, при том что рабочее дерево к этому моменту было чистым, а
названные файлы (`.github/workflows/ci.yml`, `CLAUDE.md`, `README.md`) уже лежали в истории.

Механика: hook завершается кодом 2, чтобы заблокировать остановку сессии. Сессия не может
остановиться, hook срабатывает снова, вердикт не пересчитывается против нового состояния —
и выхода из этого состояния у сессии нет. Своими средствами она не может ни исправить
нарушение (файлы вне её write set), ни прекратить работу.

Сессия при этом повела себя правильно: отказалась откатывать чужие файлы, перепроверила
состояние против `HEAD` и `git worktree list`, и вынесла вопрос lead-у вместо действия.
Если бы она «исправила нарушение», она уничтожила бы незакоммиченную работу lead-а.

Обе сессии пришлось остановить извне.

Ценность finding-а: fail-closed контроль на завершении сессии обязан иметь выход. Контроль,
который нельзя ни удовлетворить, ни отменить, останавливает работу вместо того, чтобы её
защищать, и создаёт давление на отключение самого контроля.

### F5-2 (major). Task-сессия правит скрипт hook-а, который исполняется всеми сессиями

`I00-F5-T1` по своему write set правит `tools/agent-harness/src/hooks/subagent-stop-writeset.ts`.
Этот файл — не библиотека задачи, а исполняемый скрипт, который запускается hook-ом **во всех
параллельных сессиях**, включая чужие. Промежуточное состояние файла во время редактирования
влияет на вердикты, получаемые другими задачами.

Это тот же класс, что исходный B2: источник ограничений доступен на запись ограничиваемой
стороне. Здесь — не через подмену данных, а через подмену исполняемого кода контроля.

### F5-3 (major). Параллельные сессии неразличимы ни на входе, ни на выходе

Две половины одного корня, найденные независимо:

1. **Вход.** `.claude/writeset.json` — один файл на репозиторий, поэтому параллельным
   task-сессиям нельзя выдать разные права. Раунд I00-F5 шёл на объединённом write set.
2. **Выход.** В общем рабочем дереве hook не может атрибутировать diff конкретной сессии:
   у него нет источника, который сказал бы, чьи это байты. Вердикт относится к дереву, а не
   к сессии, поэтому две невиновные сессии получили чужое нарушение.

Существенно: сейчас это редкий ложный отказ, потому что база сравнения — `HEAD`, и виден
только незакоммиченный диапазон. **После фикса B-1** (сверка от `base_commit`) hook начнёт
видеть всю чужую закоммиченную работу раунда, и ложные срабатывания станут постоянными.
То есть B-1 нельзя включать, не ответив на атрибуцию.

Отклонение по worktree зафиксировано в `PLAN.md` §8 как принятый риск I00. Эти три finding-а —
цена этого решения, предъявленная целиком.

### F5-4 (major). Агрегация карт задач даёт ложное «пересечение write sets» между итерациями

`ownership:check` в каталожной форме объединяет все `.claude/tasks/*.json` в один список задач,
из-за чего `I00-T04` и `I00-F5-T4` — одна область в **разных** итерациях — объявляются
конфликтующими владельцами. Живой прогон дал 14 таких «нарушений», ни одного настоящего.

Внутри одной итерации пересечение write sets — реальный конфликт параллельных задач. Между
итерациями — норма. CI временно переведён на явную карту текущей итерации
(`ITERATION_TASKS` в `ci.yml`); это заплатка, требующая ручного обновления каждую итерацию.

### F5-5 (minor). Контроль был доказан не полностью, и это нашла только мутация

`scan-no-llm.ts` содержит два независимых guard-а: try/catch на lockfile (собственно M-5) и
агрегатный по `unreadablePaths` из трёх источников. Первый был покрыт тестом, второй — нет:
lead снял его целиком, и `pnpm test:unit` остался зелёным на 486/486. Реализация была
правильной, недоставало только доказательства. Закрыто в `01abfa2`.

Это иллюстрация вывода раунда 3 в обратную сторону: мутационная проверка находит недоказанный
контроль там, где отчёт исполнителя выглядит полным.

### F5-6 (процессное). Lead закоммитил красный gate

Коммит `411ee51` прошёл с красным `pnpm format:check`: lead прогнал тесты и security, но не
формат. Полный gate существует именно для этого. Исправлено в `01abfa2`.

### F5-3 подтверждён на живом примере — фиксом против его же автора

Сессия `I00-F5-T1`, закончив работу над этим самым hook-ом, была им же заблокирована на
завершении. Вердикт назвал нарушениями `.github/workflows/ci.yml`, `tools/usage-continuity/**`,
`packages/contracts/**`, `README.md`, `CLAUDE.md`, `AGENTS.md`, `pnpm-lock.yaml` и
`REVIEW.md` — то есть коммиты `a11ab49` и `a4bf3e3`, сделанные lead-ом (снятие DEV-01 и перенос
контракта момента), лежащие между её якорным коммитом и `HEAD`.

Сессия проверила `git status` и `git log`, установила, что ни один из этих файлов не входит в её
diff, и **не откатила ничего**, сообщив вместо действия. Её собственный write set — 13 файлов —
не затронут.

Три вещи, которые этот эпизод доказывает лучше любого описания:

1. **F5-3 реален и не лечится точечно.** Атрибуция в общем рабочем дереве недостижима: hook
   видит диапазон коммитов, а не авторство. Автор фикса не смог защитить от этого даже себя.
2. **F5-1 исправлен и ведёт себя как задумано.** Первое появление причины заблокировало
   однократно; повторная попытка завершения прошла бы. Петли, стоившей раунду двух сессий,
   больше нет.
3. **Диагностика работает.** `session_id` и `range=<base>..HEAD` в сообщении — именно то, чего
   не хватало сессиям `F5-T2` и `F5-T3`: получатель смог за один шаг установить, что диапазон
   содержит чужую работу, вместо разбора чужого diff вслепую.

Это прямой аргумент за закрытие отклонения по worktree (`PLAN.md` §8) в I01: изоляция снимает
F5-1, F5-2 и F5-3 одновременно, тогда как по отдельности каждое лечится только смягчением,
которое реоткрывает уже закрытые findings (проверено: снятие `leadPaths` из нарушений
task-сессии реоткрывает N1).

## Верификация раунда фиксов I00-F5 (диапазон `daf148c..00515b4`)

Две независимые read-only сессии, впервые с настоящей ролью `reviewer` (`owner_role`
= `"reviewer"`, пустой `write_paths`): запись запрещена полностью, Bash read-only,
`git commit`/`push`/`stash`/`install` запрещены. Обходной путь предыдущего раунда не
понадобился.

### Test reviewer: `FAIL (1 blocker, 0 major)`

18 мутационных проб, 17 из них подтвердили честность контроля: каждая мутация красила
**прицельно предназначенный** тест без побочных провалов — B-1, F5-1, M-2, minor 5, M-8 (оба
репро), M-7 (пустой `write_paths` не стал разрешён всем, только роли `reviewer`), F5-4,
оба guard-а `scan-no-llm`, `scan-secrets`, checksum с `phase`, `collate "C"`, `addMinutes`

Восемнадцатая проба вскрыла **blocker в коде lead-а**.

#### F5-7 (blocker). Валидность дня месяца не проверялась ничем

`packages/contracts/src/instant.ts`. Генератор property-набора ограничивал день диапазоном
1–28, поэтому граница месяца физически не возникала, и `isLeapYear`/`daysInMonth` — функции
**валидации**, а не арифметики — не были покрыты вовсе. Единственным свидетельством оставался
один литеральный пример `2026-02-30`.

Две независимые мутации оставляли весь набор зелёным:

```text
isLeapYear -> year % 4 === 0      : 227/227 зелёные; 1900-02-29 и 2100-02-29 ПРИНИМАЮТСЯ
DAYS_IN_MONTH апрель 30 -> 31     : 227/227 зелёные; 2026-04-31 ПРИНИМАЕТСЯ
```

Воспроизведено lead-ом независимо до внесения фикса.

Отягчающее обстоятельство серьёзнее самого дефекта: комментарий в
`instant.property.test.ts`, написанный lead-ом, утверждал, что дифференциальная проверка —
единственный инвариант файла, привязанный к календарю. Для арифметики `daysFromCivil` это
верно; для валидации — нет, по той же причине (день не выходил за 28). Комментарий создавал
впечатление доказанного покрытия там, где его не было.

Закрыто в `d7efc12`: генератор `civilDate` даёт дни 1–31, добавлено свойство «дата принимается
ровно тогда, когда существует по независимой реализации», добавлены литеральные кейсы
(1996/2000/2400 високосные, 1900/2100/2200 нет, 31-е число в 30-дневных месяцах отвергается),
комментарий переписан.

При закрытии обнаружен второй дефект того же класса, уже в самом фиксе: первая редакция
генератора порождала сочетание «столетний год + февраль + 29-е» с вероятностью порядка 0,02%
на прогон, поэтому property краснел лишь иногда. **Мерцающий детектор хуже отсутствующего:**
он даёт ложную уверенность. Добавлены прицельные ветви к равномерной; стабильность проверена
тремя последовательными прогонами.

### Наблюдение о разделении ролей

Три раунда подряд test reviewer и architecture reviewer находят **разные** классы дефектов и
ни разу не нашли один и тот же. Раунд 3: мутационная проверка не может обнаружить отсутствующее
правило, потому что для него нет мутанта. Раунд I00-F5: мутационная проверка обнаружила
недоказанный контроль там, где отчёт исполнителя и обзор кода выглядели полными. Это довод
против слияния ролей в одну «проверку качества».
