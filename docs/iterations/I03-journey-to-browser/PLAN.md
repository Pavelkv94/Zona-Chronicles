# I03 — PLAN

Итерация: I03 «Journey до браузера»
Вход: I02B (`d6a50ba`)
Дата: 2026-08-23

## 1. Гипотеза

Один факт проходит через весь стек и понятен зрителю. До сих пор мир наблюдался только из
терминала: `world events` печатает журнал, `world state` — состояние. После I03 тот же факт
виден на экране в браузере, и увиденное совпадает с каноническим журналом.

Это первая итерация, после которой у проекта есть ПРОДУКТ, а не только движок.

## 2. Observable demo

```sh
export DATABASE_URL=postgres://zona:zona_local_dev_only@localhost:5432/zona
pnpm world migrate && pnpm world init --seed 42

# мир идёт сам: worker двигает время по скорости мира, без участия зрителя
pnpm worker &

pnpm api &          # observer API, read-only
pnpm web &          # экран

# открыть http://localhost:3000
#   - карта: четыре узла, рёбра маршрутов, агенты на узлах
#   - лента: journey.started / journey.completed по мере появления
# начать путь из CLI:
pnpm world run --agent agent:rook --route route:yard-to-bridge
#   - агент на карте становится "в пути"
#   - в ленте появляется journey.started БЕЗ перезагрузки страницы (SSE)
#   - через время мира появляется journey.completed, агент оказывается на мосту
# перезагрузить страницу — состояние восстанавливается из snapshot API, не из SSE
```

**Что демо обязано показать, а не просто отработать:** экран не влияет на мир. Закрытая вкладка,
десять вкладок или ноль — журнал одинаков. Это PR-01 и PR-04, и проверяется отдельно.

## 4. Scope

1. **Долг I02B — мир идёт сам.** `runWorldTick` в цикле worker-а; горизонт вычисляется из
   реального прошедшего времени и коэффициента скорости мира. Коэффициент — в versioned ruleset,
   не в коде и не в env.
2. **Долг I02B — BLOCKER 2.** `loadWorldState` читает мир в ОДНОЙ транзакции.
3. **Расширение контента:** обратные маршруты, чтобы мир не «заканчивался» после нескольких
   переходов. `loc:relay-station` остаётся несвязной намеренно — под критерий отказа.
4. **Проекции** (`packages/projections`): read models карты и ленты, своя `projection_sequence`,
   свои таблицы. Строятся из `outbox`, а не из канонических таблиц.
5. **Observer API** (`apps/api`): `GET /v1/world/snapshot`, `GET /v1/map`, `GET /v1/events`,
   `GET /v1/stream` (SSE, resume через `Last-Event-ID`). Роль БД — `zona_api`, без доступа к
   каноническим таблицам.
6. **Экран** (`apps/web`, Next.js): карта узлов и лента событий. Читает только `/v1/*`.
7. **Playwright journey scenario:** путь начат — виден на карте — завершился — перезагрузка
   страницы восстанавливает состояние.

## 5. Out of scope

## 7. Инварианты, которые нельзя нарушить

1. **Observer path не читает канонические таблицы.** Ни API, ни проекции при ОБСЛУЖИВАНИИ
   запроса. Построение проекции читает `outbox`, а не `world_events` напрямую.
2. **Публичный API не содержит write-маршрутов.** Проверяется `app.printRoutes()`, не намерением.
3. **Зритель не влияет на мир.** Ни числом подключений, ни их отсутствием, ни `Last-Event-ID`.
4. **Скорость мира не входит в `deterministic_runtime_profile`** — она свойство темпа, а не
   детерминизма.
5. **Проекция не является источником факта.** Расхождение проекции с журналом — сбой проекции,
   и восстанавливается она пересборкой, а не правкой.

## 9. Stop conditions

- UI читает canonical tables — STOP;
- SSE оказался единственным способом восстановить состояние — STOP;
- journey не объясним из событий — STOP;
- скорость мира изменила канонический результат — STOP.

## 10. Отклонения от этого плана

### 1. Коэффициент скорости мира — НЕ в versioned ruleset

§4.1 говорил «коэффициент — в versioned ruleset, не в коде и не в env». Сделано иначе:
версионированные данные рядом с worker-ом (`apps/worker/src/world-tempo.ts`,
`WORLD_TEMPO_VERSION`).

Причина обнаружилась при реализации. Rules bundle адресуется checksum-ом и входит в канонический
снимок — он доказывает, ПОД КАКИМИ правилами посчитан мир. Темп на канонический результат не
влияет (это и есть D2), поэтому его включение в bundle связало бы снимки с параметром, к ним не
относящимся: поворот ручки скорости менял бы checksum, и снимки, снятые до правки, объявлялись бы
несовместимыми. Мир перестал бы восстанавливаться из-за изменения темпа показа.

Это тот же довод, по которому observer-схемы не входят в schema bundle, и решать одну и ту же
развилку двумя разными способами внутри одной итерации было бы непоследовательно.

Требование §4.1 при этом выполнено по существу: значение не магическая константа в глубине цикла
и не невидимая переменная окружения — оно названо, версионировано и видно в diff.

### 2. Change request: `world init` пишет генезисный снимок

**Что изменилось.** Раньше `world init` снимка не писал, и `world replay` на свежем мире печатал
«в базе снимков не было — восстановлен из seed». Теперь снимок на `sequence 0` пишется при
создании мира.

**Почему пришлось.** Проекция начинается с генезиса, а начальную расстановку агентов НЕЛЬЗЯ
вывести из журнала: её сделал `initializeWorld` в обход событий. Единственным её источником был
`seedWorld` внутри процесса CLI. Сборщику проекции она нужна, а живёт он в worker-е — и
приложения не имеют права импортировать друг друга (`packages-do-not-depend-on-apps` и
отсутствие ребра app→app в ADR-002).

Рассмотренные и отвергнутые варианты:

- **CLI импортирует сборщик из worker-а** — прямое нарушение границы приложений;
- **сборщик переезжает в `packages/persistence`** — запрещено правилом
  `persistence-does-not-import-simulation` (оно же запрещает persistence → projections);
- **сборщик переезжает в `packages/projections`** — запрещено транзитивным
  `observer-api-does-not-reach-persistence`;
- **`seedWorld` переезжает в `packages/simulation`** — архитектурно верно и остаётся кандидатом,
  но это 76 ссылок в 14 файлах, включая acceptance и golden-и, посреди итерации;
- **отдельная колонка `worlds.genesis_agents`** — второй источник правды о том, что уже описано
  снимком.

Генезисный снимок решает то же самое существующим механизмом и даёт два побочных выигрыша: у
мира есть точка восстановления с первого дня (OPS-04), и `world replay` перестаёт нуждаться в
особом случае.

**Что НЕ изменилось.** Ветка «восстановить genesis из seed» сохранена: миры, созданные до I03,
снимка не имеют, и терять для них replay нельзя. Acceptance-тест теперь проверяет её ЯВНЫМ
удалением снимка — честной моделью такого мира, — а не отсутствием шага, которого больше не
бывает. Ослабления критерия нет: проверок стало больше, а не меньше.

### 3. Темп мира расходится с нормативной публичной скоростью

Найдено M5 независимого архитектурного аудита. Ревьюер назвал неверное число (60 — он прочитал
переопределение из E2E-стека), но расхождение реально и БОЛЬШЕ, чем он думал.

`07_MVP_MECHANICS_SPEC` §«Каноническое время»: «публичная стартовая скорость: 1 реальная минута
= 4 игровые минуты». Умолчание worker-а — одна минута мира за секунду реального, то есть 60
игровых минут за реальную: в ПЯТНАДЦАТЬ раз быстрее.

Расхождение сделано видимым, а не устранено молча:

- нормативная величина заведена константой `PUBLIC_WORLD_TEMPO` рядом с `DEFAULT_WORLD_TEMPO`;
- их отношение проверяется тестом — изменение любой из них станет осознанной правкой теста, а не
  побочным эффектом;
- `WORLD_TEMPO_VERSION` перестал быть декоративным: он читается и попадает в стартовую запись
  журнала worker-а, поэтому по логу прогона видно, под какой версией темпа он шёл.

Умолчание НЕ приведено к нормативу, и это решение владельца, а не моё. Довод за текущее значение:
§«Каноническое время» называет 4 ПУБЛИЧНОЙ стартовой скоростью — свойством запущенного мира, а не
dev-профиля, и там же прямо сказано, что «dev/test режим работает без привязки к wall clock». При
нормативной скорости сорокаминутный маршрут занимает десять реальных минут, и demo из §2 («путь
завершается, пока вы смотрите») перестаёт существовать. Довод против: норматив есть норматив, и
приоритет документов из `00_README.md` отдаёт его спецификации.

### 4. Генерация мира переехала в `packages/simulation`

Не записывалось нигде, хотя это отклонение: `PLAN.md` §10.2 перечислял этот вариант среди
ОТВЕРГНУТЫХ («архитектурно верно и остаётся кандидатом, но это 76 ссылок в 14 файлах посреди
итерации»), а сделан он был в том же коммите, что observer API (`0a90fb8`). Найдено m2
независимого аудита: докстринги `apps/cli/src/world.ts` и `world-generation.ts` ссылались на
раздел плана, которого не существовало.

Почему всё-таки переехало: генезисный снимок (отклонение 2) потребовал, чтобы порождение мира
было доступно и CLI, и worker-у, а приложения не имеют права импортировать друг друга. Оценка
«76 ссылок» относилась к переносу ВМЕСТЕ с публичным API `apps/cli/src/world.ts`; фактически
`world.ts` остался тонкой обёрткой с теми же сигнатурами, и ни один существующий вызов не
изменился.

Что осталось долгом: `apps/cli/src/world.ts` продолжает существовать только ради обратной
совместимости вызовов. Убирать его в I03 не стали — это правка, не связанная с наблюдаемым
поведением итерации.
