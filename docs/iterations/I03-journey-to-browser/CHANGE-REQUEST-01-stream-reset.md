# CR-I03-01 — `ObserverStreamResetSchema` обязана уметь сказать «доступного нет вовсе»

**Статус:** **ОДОБРЕН владельцем 2026-08-29, реализован в тот же день.** MAJOR-4 закрыт.
**Затрагивает:** `zona:observer-stream-reset/1` — ЗАМОРОЖЕННАЯ схема контракта.
**Основание:** MAJOR-4 независимой проверки тестов, раунд 2 итерации I03 (`REVIEW.md`).
**Автор запроса:** lead I03. Решение — владельца; реализация до решения не начата.

## 1. Наблюдаемое поведение

Зритель, переподключающийся с `Last-Event-ID: 42` к миру, у которого проекция ПУСТА (только что
пересобрана, либо ещё не догнала генезис), получает открытый поток, по которому не приходит
ничего. Ни кадра, ни ошибки, ни `reset_required`. Экран показывает «Поток: подключён» и молчит.

Ожидаемое поведение — то же, что при отставании за пределы окна: сервер обязан сказать
`reset_required`, зритель обязан перечитать snapshot.

## 2. Почему сейчас иначе

`apps/api/src/observer-routes.ts:268` требует `first.earliestAvailableSequence !== null`, а у
пустой проекции доступного номера нет — он и есть `null`. Условие не выполняется, и путь
`reset_required` не срабатывает.

Убрать проверку на `null` нельзя: подставить в кадр нечего.

## 3. Почему это change request, а не правка

`earliest_available_sequence` объявлен как `ProjectionSequenceSchema`, то есть
`UnitIntegerSchema(PROJECTION_SEQUENCE_UNIT)`, а у этого юнита `min = 1`. Значения «доступного
нет» в допустимом множестве не существует: ни `0`, ни `null` схему не проходят.

То есть дефект не в маршруте, а в контракте: он не способен выразить состояние, в котором мир
законно бывает. Правка маршрута без правки схемы дала бы кадр, который сам маршрут и отвергнет
собственной проверкой контракта.

## 4. Предлагаемое изменение

```diff
 export const ObserverStreamResetSchema = Type.Object(
   {
     reason: Type.Literal('reset_required'),
-    /** С какой позиции проекция ещё может отдавать события. */
-    earliest_available_sequence: ProjectionSequenceSchema,
+    /**
+     * С какой позиции проекция ещё может отдавать события; `null` — доступного нет вовсе
+     * (проекция пуста или пересобирается).
+     */
+    earliest_available_sequence: Type.Union([ProjectionSequenceSchema, Type.Null()]),
   },
   { $id: 'zona:observer-stream-reset/1', additionalProperties: false },
 );
```

Расширение множества значений, а не сужение: всякий кадр, валидный сегодня, останется валидным.

## 5. Совместимость

| | |
| --- | --- |
| Существующие кадры | остаются валидными: число по-прежнему допустимо |
| Существующие клиенты | `apps/web/src/app/observer-client.ts:16` УЖЕ объявляет тип `number \| null` — клиент готов, а контракт нет |
| `$id` схемы | сохраняется: `zona:observer-stream-reset/1` |
| Персистентность | нулевая: кадр потока нигде не хранится |
| `schema bundle` / snapshot checksum | не затронуты — observer-схемы в bundle не входят (`observer.ts`), по тому же доводу, по которому в него не входит темп |

Расхождение в строке про клиента стоит прочитать отдельно: тип на стороне зрителя УЖЕ описывает
`null`. Значит, реализация экрана исходила из состояния, которого контракт не допускает, и
несоответствие жило незамеченным по обе стороны.

## 6. Альтернативы, рассмотренные и отклонённые

**А. Понизить `PROJECTION_SEQUENCE_UNIT.min` до 0 и слать `0`.** Отклонено: `0` пришлось бы
читать как «нет доступного», то есть кодировать отсутствие числом. Тот же номер участвует в
курсоре SSE и в snapshot, и «нулевой шаг проекции» получил бы два разных смысла в разных полях.

**Б. Отдельная причина `projection_empty` рядом с `reset_required`.** Отклонено: для зрителя
действие одно и то же — перечитать snapshot. Вторая причина заставила бы каждого клиента
обрабатывать два кадра одинаково и разошлась бы при первой же невнимательности.

**В. Закрывать поток без кадра, кодом 409 до `writeHead`.** Отклонено: заголовки к этому моменту
могут быть уже отправлены, а главное — зритель не отличит «нечего отдавать» от разрыва сети.

## 7. Что сделано после одобрения

1. Красный тест ДО правки. Наблюдался красным ровно так, как описан дефект: тест не упал на
   утверждении, а ПОВИС на пять секунд и упал по таймауту — поток не завершается, потому что
   кадра нет. Симптом дефекта и симптом падения совпали.
2. Схема расширена до `Type.Union([ProjectionSequenceSchema, Type.Null()])`.
3. Условие маршрута переписано: отставание клиента — это ДВА случая, и пустая проекция второй из
   них. `cursor > 0` сохранён в обоих.
4. Мутационная проба, обе стороны:

   | мутация | падает |
   | --- | --- |
   | вернуть прежнее условие `!== null` | «пустая проекция при `last_event_id > 0`» — снова висит 5 с |
   | убрать `cursor > 0` | «пустая проекция без `last_event_id` сбросом не является» |

5. Экран проверен чтением кода: обработчик `stream.reset` payload не читает вовсе — закрывает
   поток и перечитывает snapshot. `null` для него безразличен.

## 9. Находка, сделанная при реализации

`EventPageResponseSchema` в `observer-routes.ts` описывал ТО ЖЕ поле собственной копией правила:
`Type.Integer({ minimum: 1 })`, выписанное руками вместо `ProjectionSequenceSchema`. Два описания
одного поля жили рядом, не зная друг о друге, и расходились: страница допускала `null` всегда,
замороженная схема сброса — никогда. Копия не ломается, когда расходится с оригиналом; она просто
начинает описывать другое.

Исправлено: маршрут берёт примитив из контракта, и `ProjectionSequenceSchema` добавлен в
публичный экспорт `@zona/contracts` — до этого он не экспортировался, что и толкало к копии.

## 8. Чего этот CR НЕ просит

Не просит менять `ProjectionSequenceSchema`, `ObserverEventSchema`, `ObserverWorldSnapshotSchema`,
`$id` схемы сброса и любую персистентную схему. Область — одно поле одного кадра потока.
