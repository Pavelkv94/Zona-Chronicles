# I03 — evidence

Снято ОДНИМ прогоном скриптом `scripts/evidence/capture-i03.ts` на PostgreSQL 17.5, seed 42.
Ни один файл не составлен вручную. Скрипт создаёт свою базу, свой мир и свои процессы и
удаляет их за собой — поэтому все файлы описывают один и тот же мир, а не удачную подборку.

| Файл | Что это |
| --- | --- |
| `01-initial-state.txt` | `world state` сразу после порождения из seed 42 |
| `02-refusal.txt` | Отказ D12: путь к недостижимому маршруту, exit code и названная причина |
| `03-run.txt` | `world run` — принятая команда, порождённое событие, версия мира 0 → 1 |
| `04-final-state.txt` | `world state` после того, как мир сам довёл путь до конца |
| `05-events-cli.txt` | `world events` — журнал глазами оператора |
| `06-replay.txt` | `world replay` — checksum replay и непрерывного прогона |
| `events.jsonl` | Канонический журнал из КАНОНИЧЕСКИХ таблиц, по строке JSON на событие |
| `observer-snapshot.json` | Ответ `GET /v1/world/snapshot` того же мира |
| `observer-events.json` | Ответ `GET /v1/events` того же мира |
| `screenshots/` | Четыре кадра экрана из того же прогона |

## Почему журнал и ответы API сняты отдельно

Утверждение итерации — «увиденное совпадает с каноническим журналом». Оно проверяемо только
если сравниваются файлы из ДВУХ РАЗНЫХ источников: `events.jsonl` читается из `world_events`
подключением владельца, `observer-*.json` — ответы observer API, у которого доступа к
каноническим таблицам нет вовсе (D5). Снимай скрипт оба через API — он сверял бы проекцию с
самой собой.

Сверка на этом прогоне выполнена по `event_id`, а не по порядковому номеру:

| канонический журнал | ответ observer API |
| --- | --- |
| `sequence 1`, `evt_D2ETY739KPRAYTMXP916Q7DKTN`, `journey.started`, 06:00, `loc:quiet-yard` | `projection_sequence 1`, тот же `event_id`, тот же тип, время и локация |
| `sequence 2`, `evt_4YDB3796KAR0M9CTNSVJ96NCWG`, `journey.completed`, 06:40, `loc:bridge` | `projection_sequence 2`, тот же `event_id`, тот же тип, время и локация |

`world_time` конечного состояния (06:40) равен `world_time` события `journey.completed`, а
`06-replay.txt` показывает совпадение checksum replay и непрерывного прогона.

## Что видно в кадрах

1. `01-world-at-rest.png` — мир только создан: четыре узла, четыре агента по местам, лента
   пуста, **поток живой**. Последнее важно: следующий кадр иначе доказывал бы работу
   перезагрузки, а не обновления без неё.
2. `02-journey-started.png` — БЕЗ перезагрузки: `journey.started` в ленте, Рук исчез из «Тихого
   двора» и появился в карточке «В пути» с маршрутом. Курсор проекции 1.
3. `03-journey-completed.png` — мир довёл путь сам, ни одной команды между кадрами.
4. `04-after-reload.png` — после перезагрузки то же состояние: мировое время 06:40, Рук на
   Мосту, обе записи в ленте. Восстановлено snapshot-ом, не историей потока (D11).

Мировое время на первом кадре 06:00 и на последнем 06:40 — сдвиг ровно на длительность
маршрута, а не на величину «тика»: время двигают события (ADR-004), а не горизонт.

## Дефект, найденный самой съёмкой

Первые два прогона съёмки упали по таймауту на ожидании карточки «В пути». Причина не в мире:
E2E-стек поднимался с темпом 60 минут мира за секунду реального, при котором горизонт ОДНОГО
тика перекрывает сорокаминутный путь целиком. `journey.started` и `journey.completed`
рождаются в одном тике, и состояние «в пути» не существует ни в один наблюдаемый момент.

Сценарий D13 этого не замечал: он сверяет ЛЕНТУ, а критерий D13 требует, чтобы «агент на карте
менял состояние на „в пути“ БЕЗ перезагрузки страницы». Проверка ленты этого не доказывает.
Съёмка ведётся с темпом 6, и кадр `02-journey-started.png` показывает то, чего не показывал ни
один тест.

Классификация и решение — в `REVIEW.md`.
