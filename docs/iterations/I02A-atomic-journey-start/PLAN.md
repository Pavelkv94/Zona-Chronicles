# I02A — PLAN

Итерация: I02A «Атомарный старт journey»
Ветка: `iteration/I00-harness` (см. §8, отклонение 1 — продолжение практики I01)
Дата открытия: 2026-08-22
Вход: I01 (`cfe76fc`), детерминированное доменное ядро без durable state

## 0. Решение по стратегической развилке (принято lead-ом 2026-08-22)

Владелец дал постоянное разрешение принимать решения самостоятельно и дважды обозначил
приоритет: **видимый продукт важнее harness**. Развилка «идти по master-plan или строить
вертикальный срез в обход него» решена так:

**Идём по master-plan I02A → I02B → I03, но с сокращённой церемонией.**

Почему не «срез в обход плана»: единственная видимая вещь, которую стоит показывать, — это
живущий мир в браузере (I03). Мир, который не переживает перезапуск процесса, показывать нечего:
UI над эфемерным состоянием демонстрирует не мир, а один процесс, и его пришлось бы выбросить
целиком при появлении durable state. I02A — не обходной harness, а первое звено того самого
среза: `command → durable events → state`. Дорога к экрану идёт через него, а не мимо.

Что именно сокращается (это часть решения, а не небрежность):

1. **Третьего раунда верификации I01 не будет.** `REPORT.md` I01 §6 его рекомендовал. Все
   findings закрыты и проверены lead-ом поимённо воспроизведением; I02A нагружает то же ядро
   настоящими транзакциями и конкурентными командами — это более сильная проверка, чем
   ещё один статический раунд. Риск принят: если I02A вскроет дефект ядра I01, он
   регистрируется в `REVIEW.md` этой итерации, а не задним числом в I01.
2. **Один раунд независимого ревью вместо двух ролей × N раундов.** Роли `test-reviewer` и
   `architecture-reviewer` действительно находят разные классы дефектов (шесть раундов, ни
   одного совпадения), поэтому обе сохраняются, но по одному проходу и параллельно, а не
   последовательными раундами до сходимости.
3. **Evidence package сокращён до применимого.** `artifacts/` этой итерации содержит только то,
   что итерация реально производит (schema dump, fault-injection log, migration evidence);
   `world-health.json`, `causal-chains.json`, `interventions.json` появятся, когда появится
   то, что они описывают.

## 1. Гипотеза

Первый настоящий command меняет durable state атомарно и идемпотентно: событие, состояние,
outbox и записанный результат команды никогда не расходятся — ни при отказе в любой точке
транзакции, ни при повторе той же команды, ни при конкурентном исполнении.

## 2. Observable demo

```sh
docker compose up -d postgres
export DATABASE_URL=postgres://zona:zona_local_dev_only@localhost:5432/zona

pnpm world migrate                 # схема с нуля
pnpm world init --seed 42          # мир 42 в БД
pnpm world state                   # все агенты idle, версия 0

pnpm world run --agent agent:rook --route route:yard-to-bridge
pnpm world state                   # agent:rook traveling, версия 1
pnpm world events                  # ровно одно journey.started

# перезапуск процесса ничего не теряет — каждая строка выше это отдельный процесс

# повтор ТОЙ ЖЕ команды по её command_id: прежний результат, второго события нет
pnpm world run --agent agent:rook --route route:yard-to-bridge --command-id <id из вывода>
pnpm world events
```

Без `--command-id` id выводится из (мир, агент, маршрут, версия мира), поэтому повтор при уже
изменившемся мире — это ДРУГАЯ команда, и она получает честный отказ `actor_not_actionable`.
Идемпотентность демонстрируется явным `--command-id`: это разные свойства, и demo показывает оба.

## 3. Требования (`11_REQUIREMENTS_TRACEABILITY`)

| ID | Что закрывает эта итерация |
| --- | --- |
| OPS-01 | Транзакция event/state/outbox/command result; fault injection в каждой точке; идемпотентность по `command_id`; optimistic version |
| OPS-03 | Разделение PostgreSQL-ролей: migration owner, canonical worker, projection builder, read-only api; append-only `world_events` грантами, а не соглашением |
| SIM-01 | Продолжение: canonical результат не зависит от того, прошло ли состояние через БД (checksum состояния из БД совпадает с checksum in-memory прогона) |

## 4. Scope

1. Фикстура мира: 1 агент, 2 локации, 1 маршрут (уже есть в `@zona/content` — переносится в БД,
   не переписывается).
2. `journey.start` command и `journey.started` event — контракты уже заморожены в I01, здесь не
   меняются.
3. Миграции PostgreSQL: `worlds`, `locations`, `routes`, `agents`, `world_events`,
   `command_results`, `outbox`, `schema_migrations`.
4. Роли БД и гранты (OPS-03), включая отсутствие `UPDATE/DELETE` на `world_events` у worker-роли.
5. Migration runner: применяет миграции на пустой и на существующей схеме, идемпотентно.
6. Транзакционный command handler: загрузка состояния → чистый `decide` → в одной транзакции
   события, состояние, версия мира, outbox, command result.
7. Идемпотентность по `command_id` и optimistic concurrency по `expected_world_version`.
8. Сохранение результата и accepted, и rejected команд.
9. CLI: `world migrate`, `world init`, `world journey start`, `world state`, `world events`.

## 5. Out of scope

- Scheduler, `journey.complete`, worker lease, snapshots и replay — I02B;
- projections, HTTP API, SSE, UI — I03;
- PostGIS-геометрия: локации пока идентификаторы, не координаты;
- любые механики сверх `journey.start`.

## 6. Frozen contracts итерации

Замораживаются до старта реализации и не меняются внутри итерации:

- `Command`, `WorldEvent`, `CommandRejectionCode` из `@zona/contracts` — **как есть из I01**;
- форма строки `command_results`: `(command_id, world_id, outcome, rejection_code, event_ids,
  world_version_before, world_version_after, recorded_at)`;
- порядок записи внутри транзакции и его инварианты (§7);
- имена таблиц и ролей из §4.

Изменение любого пункта — change request с записью в этом файле, как в I01.

## 7. Инварианты, которые обязана держать транзакция

1. `world_events.sequence` строго монотонен на мир, без дыр и дублей (уникальный индекс
   `(world_id, sequence)`).
2. `command_results.command_id` уникален на мир: повтор возвращает записанный результат и НЕ
   порождает второго события.
3. Число строк outbox равно числу вставленных событий, и они ссылаются на них по `event_id`.
4. `worlds.version` монотонно растёт и совпадает с `sequence` последнего события мира.
5. Отказ в любой точке транзакции не оставляет ни события, ни строки состояния, ни outbox, ни
   command result — всё или ничего.
6. Rejected команда записывает `command_result` и НЕ пишет ни события, ни outbox.

## 8. Отклонения от нормативного процесса

1. **Одна ветка вместо ветки итерации.** Продолжается практика I01: интеграция в
   `iteration/I00-harness`, отдельная ветка итерации не создаётся, пока нет второго
   параллельного исполнителя.
2. **Lead выполняет реализацию.** `10_ITERATION_MASTER_PLAN` §4 требует делегировать feature
   implementation Sonnet-subagent-ам. Здесь реализацию ведёт lead, потому что владелец прямо
   указал на непропорциональную цену процесса, а разделение ролей на одной последовательной
   задаче стоило больше, чем давало. Правило «implementer не принимает собственную работу»
   **сохраняется**: приёмку делают независимые reviewer-subagent-ы (§0.2), lead её не делает.
3. **Сокращения по §0** — записаны там, чтобы не повторять.

4. **Замок мира — row lock, а не advisory lock.** §5 `03_TECHNICAL_DESIGN` предписывает
   transaction-level advisory lock канонического мира. Реализован `SELECT … FOR NO KEY UPDATE`
   на строке `worlds`. Причина: он даёт ту же сериализацию команд одного мира, но участвует в
   обычной блокировочной дисциплине PostgreSQL (в том числе корректно взаимодействует с
   `FOR KEY SHARE`, который берут проверки внешних ключей), и его не нужно снимать вручную при
   любом пути выхода из транзакции. Отклонение записано по замечанию M-6 независимого аудита:
   само решение аудит счёл правильным, дефектом была НЕЗАПИСАННОСТЬ отклонения.

5. **Применённая миграция 0003 переписана, а не заменена новой.** Фреймворк миграций это прямо
   запрещает (`MIGRATION_CHECKSUM_MISMATCH`/`MIGRATION_NAME_MISMATCH`), и запрет правильный:
   отредактированная миграция меняет эффект на базах, где она уже применена. Здесь он нарушен
   осознанно и ровно один раз, пока поставок не существует, а все базы — одноразовые dev-копии.
   Причина: 0003 содержала пароль ролей в тексте, то есть в git, в `dist` и в неизменяемом
   checksum (M-4 аудита). Оставить его и «добавить миграцию вперёд» означало бы навсегда
   зафиксировать секрет в истории репозитория. Роли и гранты вынесены в `principals.ts` и
   применяются при каждом `world migrate`; 0003 сохранила только `revoke` для `PUBLIC`.
   **Повторение этого отклонения после первой поставки недопустимо.**

6. **Верификация шла в общем рабочем дереве параллельно с реализацией.** `pnpm task:worktree`
   был введён в I00-F5 для исполнителей, но reviewer-сессии его не используют. В результате
   SubagentStop дважды приписал architecture-reviewer-у правки lead-а, и вторая блокировка
   едва не потеряла его отчёт. Это ровно F5-1/F5-2/F5-3 из `REVIEW.md` I00, не закрытые для
   роли reviewer. Частично смягчено в этой итерации: эскалация SubagentStop ограничена двумя
   срабатываниями на сессию (раньше считалась по тексту причины, который в общем дереве меняет
   каждая чужая правка, — то есть не ограничивала ничего). Полное решение — worktree для
   reviewer-сессий — вход в I02B.

Отклонения 1–3 зафиксированы ДО начала реализации, в отличие от I01, где они попали в план
задним числом. Отклонения 4–6 записаны по ходу, в момент, когда были допущены или обнаружены.

## 9. Stop conditions

- partial commit при fault injection;
- дублирующееся событие при повторе команды или конкурентном исполнении;
- типы БД (`pg`, Kysely, `Date`, SQL) протекли в `@zona/domain` или `@zona/simulation`;
- миграция не применяется на существующей схеме или не идемпотентна;
- состояние, восстановленное из БД, даёт другой checksum, чем in-memory прогон.
