## 1. Что впервые стало возможным наблюдать

Мир перестал жить только внутри процесса. Команда меняет durable state атомарно, и результат
виден другому процессу:

```text
$ pnpm world init --seed 42
Мир world:prototype создан из seed=42; версия 0.

$ pnpm world run --agent agent:rook --route route:yard-to-bridge
Команда cmd_8B8S7CT1T6920H6HJVCM7MCN8S принята.
  события: evt_D2ETY739KPRAYTMXP916Q7DKTN
  версия мира: 0 -> 1

$ pnpm world state          # отдельный процесс, отдельное подключение
  agent:rook     traveling  в loc:quiet-yard по маршруту route:yard-to-bridge

$ pnpm world run --agent agent:rook --route route:yard-to-bridge --command-id cmd_8B8S...
Команда cmd_8B8S7CT1T6920H6HJVCM7MCN8S принята (повтор: результат прочитан из journal).
  события: evt_D2ETY739KPRAYTMXP916Q7DKTN

$ pnpm world events
Событий: 1
```

Мир по-прежнему не идёт сам: `journey.completed` требует scheduler-а — это I02B. Доказано, что
первый настоящий переход состояния переживает процесс, повтор и сбой.

## 6. Решение

Итерация прошла ДВА раунда независимой верификации: первый по плану, второй по рекомендации
архитектурного аудита. Суммарно **3 blocker, 14 major, 18 minor**; все blocker и major закрыты,
каждый — с воспроизведением дефекта исполнением до правки и, где применимо, с пробой мутацией
на новый тест. Пять minor приняты с обоснованием.

Главный урок итерации — не в коде. Второй раунд нашёл **blocker, внесённый исправлениями
первого**, и три major в новых механизмах. То есть предупреждение аудита («после правок по
blocker/major не остаётся раунда, который проверит сами правки») подтвердилось буквально, в
той же итерации, где было высказано. Сокращение церемонии до одного прохода (`PLAN.md` §0.2)
оказалось ошибкой ровно в этой части: экономия одного раунда стоила бы неработающего
обновления схемы.

Оба blocker первого раунда и blocker второго — об одном и том же классе: **доказательства не
доказывали заявленного**. Acceptance мог исполнять несобранный `dist`; разделение ролей жило
только в миграции, пока приложение ходило под SUPERUSER; путь обновления схемы не был покрыт
ничем, поэтому переиспользование id миграции прошло мимо 48 тестов. Ни один из трёх не был
дефектом доменной логики.

**Рекомендация lead: GO.** Основание — все три blocker закрыты и подпёрты контролями, которые
поймают тот же класс в следующий раз; полный gate зелёный; повторный проход по горячему пути
выполнен. Решение — за владельцем.

## 7. Что стоит знать перед I02B

- **Одна команда сейчас порождает ровно одно событие.** `decide` ставит каждому событию
  `sequence = state.sequence + 1`; команда с двумя событиями упала бы на уникальном индексе
  `(world_id, sequence)` — громко, но упала бы. Снять ограничение обязана I02B вместе со
  scheduled actions.
- **Позиции PRNG не персистятся.** `UnavailableRandomSource` в handler-е бросает исключение при
  любом розыгрыше — это намеренная ловушка: первая команда, которой понадобится случайность,
  упадёт с названной причиной, а не начнёт молча повторять одно значение.
- **Новая таблица не получает грантов автоматически** (проверено исполнением). Каждая таблица
  I02B обязана принести свои `grant` в той же миграции, иначе worker получит `permission denied`.
- **`event_id` больше не свободен.** Формат зафиксирован golden-тестами: изменение — migration.
  Ключ происхождения id — функция `eventIdOriginKey`, а не соглашение: scheduler обязан
  использовать её, иначе разойдётся молча.
- **Границы ядра — deny-list из шести имён.** `nanoid`, `uuid`, `luxon`, `axios` в
  `packages/domain` не поймает ни `boundaries:check`, ни `lint`. Инверсия в allow-list — вход
  в I02B.
- **Reviewer-сессии работают в общем дереве.** `pnpm task:worktree` покрывает исполнителей, но
  не верификацию; в I02A это дважды дало ложное нарушение владения.
- **Гранты применяются ПОСЛЕ миграций — это контракт, а не удобство.** Матрица описывает
  текущую схему, поэтому на базе предыдущей поставки `grant` на новую таблицу падает.
  Fail-closed и правильно, но порядок обязан соблюдаться.
- **Каждая новая таблица I02B приносит свою строку в `GRANT_MATRIX`** — иначе golden-сверка
  грантов упадёт, а worker получит `permission denied`.
- **Три дополнительных запроса на принятую команду** (сверка перечитанного состояния) идут
  внутри удерживаемого замка. В бюджет I02B это стоит записать (n-7).
- Роли PostgreSQL — объекты кластера, а не базы; их создаёт миграция 0003 идемпотентно, но при
  восстановлении в другой кластер их придётся создать до применения грантов.
