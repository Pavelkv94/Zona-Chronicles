# I02A — ACCEPTANCE

Итерация: I02A «Атомарный старт journey»
Заморожено: 2026-08-22, до начала реализации.
Нумерация продолжает I01 (A1–A11), чтобы ID оставались уникальными в проекте: здесь **B1–B10**.

Каждый критерий исполняем. «Проверено вручную» не является приёмкой.

## B1. Миграция применяется на пустой и на существующей схеме

**Given** база без единой таблицы проекта
**When** запускается миграционный runner
**Then** схема создана, `schema_migrations` содержит все применённые версии,
**And** повторный запуск на уже мигрированной базе завершается успешно и НЕ меняет ни схему,
ни данные (идемпотентность),
**And** запуск на базе с уже созданным миром сохраняет его строки.

Проверка сравнивает dump схемы до и после повторного прогона побайтово.

## B2. Принятая команда пишет событие, состояние, outbox и результат одной транзакцией

**Given** мир, инициализированный из seed, агент в статусе `idle`
**When** исполняется `journey.start` по маршруту из его текущей локации
**Then** в `world_events` ровно одна строка `journey.started` с `sequence = 1`,
**And** `agents` показывает статус `traveling` и `route_id` маршрута,
**And** `worlds.version` равна `1` и совпадает с `sequence` последнего события,
**And** в `outbox` ровно одна строка, ссылающаяся на этот `event_id`,
**And** в `command_results` строка с `outcome = 'accepted'` и списком `event_ids`.

## B3. Повтор команды идемпотентен

**Given** уже исполненная команда с `command_id = X`
**When** та же команда с тем же `command_id` исполняется снова
**Then** возвращается ЗАПИСАННЫЙ результат первой попытки (тот же `event_ids`,
та же `world_version_after`),
**And** число строк в `world_events`, `outbox` и `command_results` не изменилось,
**And** это верно и когда повтор приходит с уже устаревшим `expected_world_version`:
идемпотентность проверяется ДО optimistic-версии, иначе повтор превратился бы в отказ.

## B4. Отказ записывается и не порождает событий

Каждый из перечисленных отказов проверяется отдельно:

| Случай | Ожидаемый `rejection_code` |
| --- | --- |
| маршрут не существует | `route_unavailable` |
| маршрут не начинается в локации агента | `route_unavailable` |
| агент не существует | `actor_not_actionable` |
| агент уже `traveling` | `actor_not_actionable` |
| `expected_world_version` устарела | `stale_world_version` |

**Then** в `command_results` строка с `outcome = 'rejected'` и этим кодом,
**And** в `world_events` и `outbox` НЕ появилось ни одной новой строки,
**And** `worlds.version` не изменилась.

## B5. Отказ в любой точке транзакции не оставляет частичной записи

Инъекция сбоя выполняется ПОСЛЕ каждого шага записи по отдельности: после вставки события,
после обновления агента, после обновления мира, после вставки outbox, после вставки
command result, и непосредственно перед `COMMIT`.

**Then** для каждой точки: состояние базы побайтово равно состоянию до попытки,
**And** повторное исполнение той же команды после сбоя проходит нормально и даёт ровно одно
событие (сбой не «съел» `command_id`).

Проба обязана сначала доказать, что сбой действительно произошёл в заявленной точке (правило
мутационной пробы, I01 PLAN §8): тест падает, если инъекция не сработала.

## B6. Конкурентные команды не создают дыр и дублей

**Given** мир версии `N`
**When** две команды с разными `command_id` и одинаковой `expected_world_version = N`
исполняются конкурентно
**Then** ровно одна принята, вторая отклонена с `stale_world_version`,
**And** в `world_events` ровно одна новая строка, `sequence` без дыр и дублей,
**And** уникальный индекс `(world_id, sequence)` не нарушен.

Проверка выполняется на настоящих параллельных соединениях, а не на последовательных вызовах.

## B7. Append-only исполняется грантами, а не соглашением (OPS-03)

**Given** соединение под ролью canonical worker
**When** выполняется `UPDATE` или `DELETE` над `world_events`
**Then** PostgreSQL отказывает по правам,
**And** та же роль успешно выполняет `INSERT` и `SELECT`,
**And** роль read-only api НЕ может читать `world_events`, `agents`, `worlds`
(observer path не читает канонические таблицы — OPS-02, здесь проверяется на уровне грантов),
**And** application-роли не имеют DDL.

## B8. Прохождение через базу не меняет канонический результат (SIM-01)

**Given** мир, порождённый из seed `S` в памяти
**When** тот же мир записан в базу и прочитан обратно
**Then** checksum состояния совпадает с checksum in-memory прогона,
**And** это верно и после исполнения одной и той же команды обоими путями:
`decide`/`evolve` в памяти и через транзакционный handler дают одинаковое состояние.

## B9. Состояние переживает перезапуск процесса

**Given** journey, начатый одним процессом CLI
**When** процесс завершился и запущен новый
**Then** `world state` нового процесса показывает того же агента в статусе `traveling`,
**And** `world events` показывает ровно одно событие.

Проверка порождает настоящие процессы, а не переиспользует пул соединений в одном.

## B10. База не протекла в домен

**Then** `pnpm boundaries:check` зелёный,
**And** `@zona/domain` и `@zona/simulation` не зависят от `pg`, `kysely`, `@zona/persistence`
ни в `package.json`, ни в импортах,
**And** доменные типы не содержат `Date`, SQL-строк и типов драйвера.

## Что НЕ является приёмкой

- зелёный `pnpm verify` без запущенной базы (интеграционные тесты в него не входят);
- «транзакция выглядит корректной» без fault injection;
- идемпотентность, проверенная только повтором в одном процессе.
